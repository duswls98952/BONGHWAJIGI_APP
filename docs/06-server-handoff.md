# 서버팀 연결 체크리스트

이 문서는 앱의 최신 요구를 서버팀에 전달하기 위한 계약 차이 기록입니다. 서버 저장소의 API를 자동 변경하거나 구현 완료로 처리하지 않았습니다.

## 기존 API로 연결할 부분

- 대응 단계와 행동: ResponseSnapshot의 `personal_response`, `actions`, revision.
- 서버 대화 텍스트: `assistant_utterance`, `voice-turns`의 transcript/utterance. 음성 바이너리가 필수인 계약이 아닙니다.
- 실시간: updates long poll과 response.updated/voice_turn.ready. 새 정보가 생기면 대기 요청에 즉시 응답합니다.
- 2D 경로: 기존 route URL을 재사용. 좌표의 경도·위도를 평면 지도에 표시합니다.
- 푸시: FCM/APNs 토큰. 앱은 `getDevicePushTokenAsync`를 사용합니다.

## 연결 전에 확정할 항목

| --- | --- | --- |

| 119 | 초안 생성·미리보기, 사용자 조작 문자/전화, 접수와 전송 구분 | 안내 버튼만 있음. 실제 연락은 하지 않음 |

## 실시간 일관성

서버는 새 개인 안내가 준비되면 **같은 revision 안에** 단계·문장·행동·입력 버전을 포함해야 합니다. 이벤트에 실린 resource_revision보다 GET 응답이 뒤처지지 않아야 합니다. 프로필·위치·현재 상태가 바뀌면 반영된 input_versions를 제공하고, 기존 경로는 무효화합니다.

공식 경보는 개인 평가보다 먼저 제공할 수 있어야 합니다. 최신 공식 alert의 수정/해제가 response 안의 복사본보다 우선합니다. 여러 경보가 있을 때 home의 ID 배열을 같은 인덱스로 연결하지 않습니다.

## 푸시 payload

기존 `PushPayload`를 사용합니다. provider의 data 값이 문자열만 허용되면 `payload` 키에 논리 JSON 전체를 직렬화하는 방식을 우선 합의합니다. 현재 앱은 이 형태와 기존 필드 형태를 읽습니다. 알림 본문에 상세 건강정보·위치 이력·전체 행동요령을 넣지 않습니다.

표시할 title/body와 논리 data를 함께 제공해 백그라운드에서 OS 알림이 가능하도록 합니다. data-only silent push를 영구 백그라운드 실행 수단으로 보지 않습니다. 앱은 임의 URL 대신 검증한 alert_id/response_id만 라우팅에 사용합니다.

## 통합 인수 시나리오

1. 공식 경보만 먼저 도착하고 개인 평가는 pending인 상황.
2. 같은 사건의 대응 단계·서버 문장이 갱신되는 상황.
3. 예전 response/turn/route가 늦게 도착하는 상황.
4. 프로필·위치·현재 상태 변경 후 경로를 보류하고 새 안내를 받는 상황.
5. 화면 잠금·타 앱 전환·푸시 누름·앱 종료 후 재실행.
6. 401·409·410·429·네트워크 단절·권한 철회.
7. 앱 TTS가 새 문장으로 교체되고 화면 이탈·만료 시 중단되는 상황.
8. 지도 키 없음·유효하지 않은 경로·접근성 unknown·현재 위치 미확인.

완료 여부는 실제 서버와 단말로 기록합니다. 문서·모의 서버·번들 검사를 통과한 것만으로 실운영 안내가 검증됐다고 표시하지 않습니다.
