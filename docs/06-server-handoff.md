# 앱·서버 통합 인계

2026-11-01 KST 기준. 앱은 [현재0.2 계약](02-api-integration.md)으로 갱신했다. 구현 코드, 서버 배포, 실제 단말 성공은 구분한다. 연결 휴대폰에서의 최종 결과와 APK 위치는 [검증 기록](07-validation.md)에 남긴다.

| 항목 | 서버·앱 반영 내용 |

## 일관성 확인

서버는 한 snapshot에 개인 단계·행동·발화·입력 버전·유효기간을 함께 제공해야 한다. 프로필·위치 응답의 input_revision, 상태 수락의 context_revision이 실제 정책에 반영되기 전에 오래된 행동을 최신으로 표시하면 안 된다.

`/me/updates` response 이벤트는 사용자에게 공개한 response ID를 반환한다. 현재 FCM response payload는 incident ID를 사용하므로 Home의 관계로 해석한다. FCM alert payload는 발송 시 Home과 같은 사용자별 opaque ID로 변환한다. 공식 경보의 ID·incident_id·response_id는 배열 순서가 아닌 명시 관계로 연결한다. 서버 ID 변환 검증은 실제 Firebase 전달·기기 알림 선택 검증을 대신하지 않는다.

현재 FCM data는 mode/resource_type/resource_id/revision만 포함한다. 이전0.1 PushPayload·중첩 payload JSON을 현재 계약으로 취급하지 않는다. 알림 원문과 상세 상태는 사용자 인증 API에서 다시 가져온다. 정밀 위치·건강 메모·전체 행동은 FCM data에 넣지 않는다.

## 실제 서버·단말 인수 순서

1. 시연 등록 설정, 동의 저장, 계정 발급, refresh rotation, 로그아웃·재실행을 확인한다.
2. 프로필 저장·충돌·선택 건강 정보 철회·삭제를 검증한다.
3. 공식 경보가 먼저 도착하고 개인 정책이 pending인 상태에서 원문이 표시되는지 확인한다.
4. 합성 시나리오의 경고→대피→위급 정책에서 단계·발화·행동이 함께 갱신되는지 확인한다.
5. 입력 수락 직후 이전 정책이 보류되고 새 input_versions 확인 후 표시되는지 확인한다.
6. 다른 계정 접근, 이전 요청의 늦은 도착, 401/409/410/429, 연결 단절·복구를 검사한다.
7. 실제 위치는 사용자가 허용한 경우에만 전송하고 만료·삭제·권한 거부를 확인한다. 합성 좌표를 실제 GPS처럼 표시하지 않는다.
8. 전경/백그라운드·재실행·TTS를 확인한다. 실제 FCM은 설정 준비 후 별도 시험한다.
9. APK의 앱 버전·API 주소·서명·설치·재실행·접근 경로를 기록한다. 실제119 연락은 수행하지 않는다.

구현과 자동 검증 근거는 [앱 구현 기록](09-app-implementation.md), 실제 연결과 단말 결과는 [검증 기록](07-validation.md)에 남긴다.
